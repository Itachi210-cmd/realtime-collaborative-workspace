## 3. Key Implementations

### Part A: Distributed Presence & Awareness
1. **Awareness Pub/Sub Channel (`collab:room:<pageId>:awareness`):**
   - Implemented `publishAwareness(pageId, awarenessBytes)` and `subscribeAwareness(pageId, cb)` in `src/server/collab-redis.mjs`.
   - Rooms listen to their dedicated Redis awareness channel upon initialization and unsubscribe on room disposal.
2. **Infinite Echo Loop Prevention (`origin === 'redis'`):**
   - Updates generated by local WebSocket clients trigger `room.awareness.on('update')`, which broadcasts to local peers and publishes to Redis.
   - Remote updates received from Redis are applied using `awarenessProtocol.applyAwarenessUpdate(room.awareness, awarenessBytes, 'redis')`.
   - The awareness update handler checks `if (origin !== 'redis')` before publishing to Redis, strictly eliminating republishing feedback loops.
3. **Server-Side Identity Binding & Deterministic Color Assignment:**
   - In `src/server/collab-persistence.mjs`, `sanitizeAwarenessUpdate` enforces that every client awareness frame binds strictly to verified Jose JWT claims: `userId`, `userName`, and `role`.
   - Deterministic collaborator colors are calculated using the 8-color palette and DJB2 hash algorithm matching `src/lib/collab/collab-colors.ts`, ensuring consistent cursor and avatar colors across all instances regardless of client-side payloads.
4. **Immediate Disconnect & Graceful Shutdown Cleanup:**
   - The server tracks active `clientID`s associated with each WebSocket connection in `ws.collabAwarenessClientIds`.
   - On client disconnect, `awarenessProtocol.removeAwarenessStates` immediately removes the user's presence state from the room's awareness. This removal triggers `awareness.on('update')`, propagating null states across Redis and destroying ghost cursors on other server instances within milliseconds.
   - On server shutdown (`server.close()`), all controlled client awareness states are cleared and broadcast via Redis before closing connections.

### Part B: Distributed Persistence Coordination
1. **Distributed Persistence Lock (`collab:lock:persist:<pageId>`):**
   - Implemented `acquirePersistenceLock(pageId, ttlMs)` in `src/server/collab-redis.mjs` using atomic Redis `SET key token NX PX ttlMs` with atomic Lua script token release (`DEL if ARGV[1] == GET(KEYS[1])`).
   - `executeSaveDirect` acquires this lock before executing PostgreSQL upserts, serializing database writes across all active server instances.
2. **Cross-Instance Notification (`yjs_persisted`):**
   - When any instance persists a document to PostgreSQL, it publishes a `yjs_persisted` notification containing `stateVersion`.
   - Listening instances update their `room.lastSavedVersion`, mark `room.hasUnsavedChanges = false`, and dismiss redundant scheduled debounced saves.
3. **Distributed Restore Mutex (`collab:lock:restore:<pageId>`):**
   - In `POST /internal/rooms/:pageId/restore`, the server queues locally and acquires a distributed restore lock with a 15-second TTL.
   - If a concurrent restore is currently active on another instance, the lock attempt fails and immediately responds with `409 Conflict: Document restoration is currently in progress on another server instance`.

### Part C: Distributed Room Lifecycle
1. **Independent Hydration & Simultaneous Access:**
   - Each server instance hydrates rooms independently from PostgreSQL (`DocumentState.yjsState`) when the first local client connects.
   - Redis Pub/Sub immediately bridges documents once loaded, allowing simultaneous editing across instances without shared in-memory state.
2. **Localized Room Cleanup:**
   - When all clients disconnect from an instance, that instance starts its local cleanup grace timer (default: 30 seconds).
   - If clients remain active on another instance, that second instance continues serving edits unaffected.
   - When the cleanup timer fires, the instance flushes any pending edits, destroys its local `doc` and `awareness`, and unsubscribes from Redis.

## 5. Manual Testing Verification Guide

To manually verify multi-instance collaboration with distributed presence:

1. **Verify Infrastructure:**
   Ensure Docker containers are running:
   ```powershell
   docker compose ps
   ```
   Redis should be running on port 6379, and PostgreSQL on port 5432.

2. **Start Collaboration Server Instance 1:**
   In Terminal 1:
   ```powershell
   $env:COLLAB_PORT = "1234"
   $env:COLLAB_INSTANCE_ID = "collab-inst-1"
   node src/server/collab-server.mjs
   ```

3. **Start Collaboration Server Instance 2:**
   In Terminal 2:
   ```powershell
   $env:COLLAB_PORT = "1235"
   $env:COLLAB_INSTANCE_ID = "collab-inst-2"
   node src/server/collab-server.mjs
   ```

4. **Verify Health Endpoints:**
   In a browser or PowerShell:
   ```powershell
   Invoke-RestMethod http://localhost:1234/health
   Invoke-RestMethod http://localhost:1235/health
   ```
   Both endpoints will return `status: "ok"`, `redis: { status: "ready" }`, and their distinct `instanceId`.

5. **Start Next.js Application:**
   In Terminal 3:
   ```powershell
   npm run dev
   ```

6. **Browser Multi-Instance Testing:**
   - **Browser Window 1:** Sign in as User A (e.g. Owner). Open a document. Point the client to `ws://localhost:1234`.
   - **Browser Window 2:** Sign in as User B (e.g. Editor) in an incognito window. Open the same document, pointing to `ws://localhost:1235`.
   - **Observe Awareness & Cursors:**
     - User A's avatar appears in the top-right collaborator avatar bar on Window 2 with their deterministic color and name.
     - Moving the cursor or selecting text in Window 1 immediately moves the colored cursor flag in Window 2.
     - Typing in Window 1 synchronizes in real time to Window 2 via Redis Pub/Sub.
   - **Observe Disconnect Cleanup:**
     - Close Window 1. Within 1 second, User A's avatar and cursor disappear from Window 2 without leaving ghost cursors.
   - **Observe Persistence & Restore:**
     - Restore a historical version from Window 2. The document updates live in Window 1 and PostgreSQL without reload.
